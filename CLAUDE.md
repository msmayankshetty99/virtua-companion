# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Riko is a local desktop AI companion with a VRM avatar.
- **Python backend** (`Code/`, FastAPI/uvicorn on `127.0.0.1:8765`) owns conversation, in-process llama.cpp inference, microphone capture/ASR, TTS playback, memory, tools and persistence. Core package: `Code/process/app_core/` (written `app_core/` below). Entry points: `Code/run_server.py` (backend), `Code/desktop_server.py` (FastAPI app), `Code/discord_bot.py`, `Code/task_mcp_server.py`.
- **Electron + React + three.js** (`electron/`) owns every window, the avatar and the UI, and talks to the backend only over HTTP/WebSocket.

This layout is on `main` (formerly the `rewrite-2` branch). `origin/llama.cpp` is an older pre-rewrite tree, kept for reference, whose tip fails to parse (`Code/process/llm_scripts/module.py:238`). `old llm_scripts/` here is dead code (the space in its name makes it unimportable).

### Native llama.cpp bridge

`tools/llama_cpp/README.md` (PowerShell-oriented) is the reference. Check out llama.cpp at `b92761a515ea31e852e7fbc1fad5f874b46f3718`, run `git apply --check` and then `git apply` with `tools/llama_cpp/emotion-probe.patch`, then:

## Architecture

### Process model
- **Dev:** backend and Electron start separately; Electron never starts or stops Python. **Packaged:** Electron spawns and stops the frozen backend.
- Python child processes: a fresh interpreter per built-in tool call (`app_core/tools/worker.py`, `--tool-worker` when frozen), stdio MCP servers from `mcp.json`, and the Discord client (`--discord-worker` when frozen). `run_server.main` dispatches those worker flags before uvicorn or the config loads (`uvicorn`, `Server` and `load_config` are lazy module attributes there). GPT-SoVITS is always a separate HTTP server.
- Every Electron window loads the same Vite bundle, routed by URL hash in `electron/src/main.jsx`: `#/overlay` (transparent click-through avatar layer), `#/control` (chat/settings; "closing" collapses it to a dock), `#/whiteboard`, `#/effects`, `#/setup` (packaged first run), `#/neural-data`.
- One `electron/preload.cjs` exposes every `contextBridge` API to every window. The `ipcMain` handlers in `electron/main.cjs` check that `event.sender` owns the request; new handlers must do the same.

### Startup and service assembly
- `run_server.main` chdirs to `$RIKO_DATA_DIR` (default: repo root), loads config, configures logging, then imports `desktop_server`. That import itself calls `load_config()` and builds `DiscordLauncher`, `GPUMonitor` and `WhiteboardImages`, so tests stub `load_config` before the first import (see `tests/test_desktop_api.py`).
- The FastAPI lifespan calls `create_chat_service` (`app_core/factory.py`), which builds everything inside an `ExitStack` that rolls back on failure: `ActionController` → optional Julia emotion engine → `create_provider` (+ the optional emotion probe's `ProbeHook`, attached before the model loads) → `provider.warmup()` (loads the GGUF, no timeout) → `TaskStore` / `ToolRegistry` → `MemoryStore` (reflection lane, `capabilities.background_parallelism`, the provider's `count_text_tokens`) → `ChatService`, which gets the factory's collaborators as a frozen `ChatDeps` (action controller, task store and MCP, initiative lane, live `context_limit`, emotion worker, `DesktopServices`) and whose `close()` owns the ExitStack. Then come `SessionManager`, `warm_session` (ASR/VAD/wake/TTS, bounded by `runtime.startup_timeout_seconds`), `ConversationStore`, `Initiative` and the resource/task-file watchers, and finally `runtime.ready` is published.
- `run_server.py` binds 127.0.0.1:8765 before the model loads (retrying for 20 s while a previous backend exits) and mints the API secrets right after; connections queue until lifespan startup finishes, so requests hang rather than fail while the model loads.
- With `desktop.setup_on_startup_error: true`, a failing `create_chat_service` or `SessionManager` construction (the loaded chat is closed first) leaves only the settings/status/resource/media routes up (the rest return 503) so Settings can repair the YAML.
- Shutdown: `run_server.Server.shutdown` first cancels the active turn (`desktop_server.stop_turn`, bounded 1 s), then uvicorn drains for 2 s; the lifespan stops Discord in parallel with `close_bounded(session, 8)` (`app_core/kernel/lifecycle.py`; a hung close is abandoned to a daemon thread) → unwind the ExitStack. An atexit guard in `llama_native.py` destroys live native contexts, or `os._exit`s when one cannot be destroyed, because ggml-metal's static destructor aborts on leftover Metal buffers. The whole sequence stays under Electron's 15 s.

### Threading and events
- `event_bus` (`app_core/events/bus.py`) is synchronous: listeners run on the publisher's thread, their exceptions are swallowed, and every event carries a monotonic `sequence`.
- `SessionManager` (`app_core/runtime/session.py`) serialises foreground turns with a `TurnGate` (`app_core/kernel/turns.py`; `present_initiative` only tries it). A second turn raises `TurnBusy` (`app_core/kernel/cancellation.py`, a `RuntimeError` keeping the old message `'Riko is already handling another turn'`), which every route (`/api/chat`, `/ws/chat`, `/api/discord/chat`) maps to 409 by type, never by text; voice turns instead wait for the gate (`respond(wait=...)`, which raises `TurnCancelled` when the session closes or `wait()` turns true). Input is recorded in `DesktopState` only once the turn is taken. The `_voice_lock` RLock guards voice/playback state, and bus listeners can take it. Lock order is `_capture_lock` (request handlers only) → `_voice_lock` → component locks. **Never publish or run callbacks while holding a component lock**: queue them on an `Outbox` (`app_core/events/outbox.py`) and call `flush()` after releasing it. `tests/test_lock_discipline.py` enforces this with a static scan and deadlock regressions.
- Busy and idle have one definition: `SessionManager.status()` returns a frozen `RuntimeStatus` (`kernel/turns.py`; read under `_voice_lock`, or with `locked=False` from a callback that may run under a provider or tool lock, such as initiative's cancel poll and the probe's `provider.expression_idle()`, which SessionManager sets with `set_expression_idle`), and its predicates (`replying`, `local_reply`, `is_quiet`, `idle_for_background`, `model_state`) serve the avatar, wake feedback, initiative, the emotion probe, the calibration guard and `voice_anchor`. Other modules use only public session methods: `status()`, `is_open`, `active_turn()`, `cancel_turn(turn_id)` (Discord's `/stop`), `set_user_speaking()` (VoiceInput's VAD), `transcribe(pcm)` and `history_snapshot()`; `tests/test_session_surface.py` fails on any reach-in. Collaborators are passed, not patched on: `ChatService` takes `ChatDeps` and, per turn, a `TurnContext` (`kernel/turns.py`: origin, runtime observation, memory context, `emotion_from_playback`); desktop tools take `DesktopServices` (`desktop/tools.py`; SessionManager attaches `avatar_motion`); the probe asks `EmotionWorker.playback_active`. `ChatService`, `DesktopState` and `RuntimeConfig` have `__slots__`, so setting an undeclared attribute fails (`tests/test_declared_attributes.py`, which also bans `getattr` defaults for the retired names). Providers are used only through their declared members (Inference, below). `tests/test_private_access.py` pins every cross-object `_name` access (direct or through `getattr`/`setattr`/`hasattr`/`delattr` with a literal name) in app_core and `Code/*.py` per file, so a new one fails (and a removed one must be dropped from its list).
- Background work uses `DaemonExecutor` (`app_core/kernel/workers.py`; bounded queue, daemon threads). Each turn is cancelled through its own `threading.Event` and `TurnCancelled`; preempted background inference raises `BackgroundPreempted` (memory's `ReflectionDeferred` subclasses it). Both live in `app_core/kernel/cancellation.py` and derive from `Deferred` (stopped on purpose, not failed).

### Inference
- The provider contract is `inference/provider.py`: `InferenceProvider` (generate, stream, `count_tokens`/`count_text_tokens`, warmup, `cancel` (the live request only), `set_foreground`, `set_pause_background`, `set_expression_idle`, close, `lanes` (live, initiative, reflection) and `capabilities`, a `ProviderCapabilities(slots, exact_tokens, latent_probe)`). `BaseProvider` defaults every member but generate (one lane for every role, estimated counts, no-op lifecycle), every provider and test fake subclasses it, and no caller `hasattr`/`getattr`s a provider (`tests/test_provider_contract.py` scans for it). The probe's members are behind `provider.probe_host`, a `ProbeHost` (only `InProcessLlamaProvider`; else None): `attach_probe(hook, interval)`, `probe`, `probe_error`, `replay_lane`, `set_probe_interval`, `probe_idle`. Each generation notifies the provider's `GenerationObserver`s (`on_start`/`on_event`/`on_finish` with a `Generation`: role, slot, group, packed messages; a failing observer is logged and never fails the request). `emotion/probe_hook.py`'s `ProbeHook` is the observer that parses `riko.emotion_probe.sample` and the one home of `FEATURE_VERSION`/`FEATURE_WIDTH` (the patch repeats the version; `tests/test_release_build.py` compares them), so inference/ imports nothing from emotion/.
- The probe starts after the model has loaded, in its own `try`: a stale library (`/props` reporting another `FEATURE_VERSION`), missing torch, a Julia load failure or an unreadable file leaves the model up with `probe` None and `probe_error` set, which `/api/neural/status` returns; restart Python to retry. Its identity's GGUF and library fingerprints are cached per process by each file's (path, size, mtime) (`llama_context.fingerprint`), and its keys and values name existing probe data, so never change them. `EmotionProbe` reads Julia only through `ensure_loaded()`, `question_set()`, `resolved_source` and `fingerprint()`, and `EmotionProbe.replay(examples, lane)` runs `/api/neural/replay` on `replay_lane`.
- `create_provider` (`app_core/inference/providers.py`) picks the provider:
  - `llama_cpp` → `InProcessLlamaProvider` (`llama_native.py`). It calls the C ABI in `tools/llama_cpp/riko-native.cpp` via ctypes: five `riko_*` exports, serving only `/v1/responses`, `/apply-template`, `/tokenize`, `/props` and `/slots`, with argv from `native_arguments` in `llama_context.py`. There is no HTTP listener, llama-server or llama-cpp-python, and no fallback: `runtime.native_library` is required.
  - `llama_server` → `LlamaServerProvider` (`llama_server.py`): the same `LlamaContextProvider` protocol (slot 0 for live, exact `/apply-template` + `/tokenize` counts, `/v1/responses` streaming and tools) against a llama-server the user runs at `runtime.base_url` (default `http://127.0.0.1:8080`; validated by `server_address` in `llama_runtime.py`). It uses `http.client`, one connection per request, and cancels by shutting the socket down (closing alone does not wake a read blocked during prefill). Startup waits on `/health` (503 while loading), then requires exactly `parallel_slots` slots each holding the largest of the live, initiative and reflection budgets, and prints the matching `llama-server` command otherwise; a connection failure resets it so the next request checks again. The server owns the model and GPU settings, and there is no emotion probe.
  - `openai`, `lm_studio`, `openai_compatible`, `ollama`, `local_http` → `OpenAIProvider`: Responses API with a Chat Completions fallback, calibrated token estimates (`context_budget.estimate_tokens`, roughly 1.2-1.5x real counts), no slots. Stop is per request: `cancellable_stream` makes the request on a helper thread and shuts its socket down when the turn's `cancelled()` turns true (initiative and reflection share the provider, so there is no provider-wide cancel). Both provider families fold mid-conversation system messages with `responses.template_messages` (strict chat templates reject a later system message), which also joins consecutive user (or plain assistant) messages, because history keeps the user's message of a stopped, failed or unheard turn and Gemma/Mistral templates require alternating roles.
- `SlotScheduler` (`llama_context.py`) reserves slot 0 for the `live` lane. `initiative` and `reflection` share slots 1..N-1 (`runtime.parallel_slots`, 2–4), at most one `initiative` at a time (`kv_budget.suggested_pool` sizes a unified KV pool for one, and an overflow aborts every slot), and live turns preempt them when `runtime.pause_background_on_live` is set. The emotion probe captures only on slot 0; `probe_replay` (example replay) takes slot 0 only while no live request wants it, a foreground turn or a queued live request preempts it whatever that setting says, and `cancel_live` (Stop) reaches only a `live` lease.
- `--ctx-size` comes from `kv_budget.pool_capacity`. `runtime.flash_attn` is `auto`/`on`/`off` (YAML booleans mean on/off); `n_gpu_layers` -1 lets llama.cpp `--fit` keep 1 GiB free, -2 requires every layer, and only -1 passes `--fit on`. `split_mode: row` loads but the native provider refuses it. Budgets above the GGUF's training context fail before loading, and `riko_create` returns llama.cpp's own WARN/ERROR lines on failure and its offload/flash-attention notes on success. Per-role budgets are enforced only by Python-side packing (`context_budget.pack_context`, with exact native token counts) and by `max_output_tokens`. `pack_context` keeps an anchor per `ChatService` (`context_state`) so a steady turn costs one count and the history prefix stays stable between trims (trim to 3/4 of history's room, re-expand below 1/2); as a last resort it truncates oversized tool results with a marker. The tool loop adds a runtime observation only when the runtime state (not its timestamp) changed and keeps the ones it sent, so each tool-loop request extends the previous one; memory captures store a bounded `formation_context`, and `task_get` returns a summarised, limited change history.
- Turn flow: `SessionManager.respond` → `ChatService.respond` (`app_core/conversation/chat.py`):
  1. memory capture and recall;
  2. the prompt: a stable system + history prefix (so the KV cache is reused), then `context_kind='optional'` system messages;
  3. `provider.generate`, which streams deltas;
  4. the `ToolRegistry` loop, up to `tools.max_iterations`;
  5. commit the turn to `chat.conversation`, which SessionManager then rewrites for speech over the reply or a cut.
- The native context is allocated once, so changing `n_ctx`, `parallel_slots`, the KV pool or the initiative/reflection budgets needs a Python restart. A native crash kills the whole backend.
- The llama.cpp pin and the patch's five-file footprint are enforced by `tests/test_release_build.py`.

### Voice pipeline
- The mic opens only on `/api/voice/start|activate` or `/api/mic/toggle`. `VoiceInput` (`app_core/audio/voice_input.py`) runs these threads:
  1. `microphone-capture`: sounddevice, 16 kHz mono int16, 512-sample frames.
  2. `voice-vad`: Silero VAD, `WakeWord` (EfficientWord-Net ONNX on CPU) and `VoiceSegments`. The wake phrase is `voice.wake_word`, else the first word of `presets.default.name`; an unusable one (several words, not text) disables only wake detection (`WakeWord.unavailable`, reason in wake status), never startup.
  3. `voice-asr`: faster-whisper through `session.transcribe`: the session's one model (`AsrService` in `app_core/audio/asr.py`, built once and shared with startup warmup and Discord's `/transcribe`).
  4. `voice-turn`: calls `SessionManager.respond`. `SessionManager.voice_transcript` returns a disposition that `VoiceInput` acts on: `fresh` (a new turn: no spoken reply in flight, a remote `speak=False` reply, a stale anchor, or a reply already finished or stopped), `reply` (the words were merged into the input or inserted as `[speaking over you]` at the cut, and the cut reply is redone with `record_user=False, reply_to=<turn>`; if another turn ran first, the redo takes those words back out of the cut turn's history and asks them as a new turn, so they are recorded once), `preserved` (tolerated speaking-over) or `ignored`.
- Output: streamed deltas → `SpeechChunks` (`speech.max_words`) → `SpeechQueue` (`app_core/audio/speech.py`) → GPT-SoVITS over HTTP (`sovits_ping_config.url`) → raw PCM16 played by sounddevice. `sovits_ping_config.sample_rate` must match the server.
- Barge-in uses the character offsets of spoken chunks. `Interjections` cancels after `voice.interruption_seconds`, and history is rewritten at the estimated cut point. There is no echo cancellation. `speak=False` turns (Discord) never engage the wake window or anchor local speech.

### Persistence
The data root is the directory holding `character_config.yaml`.
- `persistent_memories/` is user data: never delete it during cleanup. Runtime files:
  - `chat_history.json`: the model's context, with one writer: `ConversationHistory` (`app_core/conversation/history.py`, `chat.conversation`). `ChatService` appends a finished turn, `SessionManager` rewrites one (speech over a reply, a cut, a stale redo) through `replace`/`rewrite`, and readers take `snapshot()` (`chat.history` is a copy). Each change is one step under its lock (a leaf below `_voice_lock`) and rewrites the whole file (fsynced) before releasing it; a failed save is logged, not raised, and the next change retries. An unreadable file is kept as `chat_history.json.unreadable-<timestamp>` before anything replaces it. Only a turn still generating or playing is cut by Stop/Sleep/shutdown; failed and cancelled turns keep the user's message.
  - `memory_store.json` (`app_core/persistence/memory.py`): a list of memories (version 1) or `{"version": N, "records": [...]}`, written in the layout it was read in (older builds read only the list) and wrapped only once `STORE_VERSION` is bumped, with a `STORE_MIGRATIONS` step. Unknown keys are kept and written back; a wrongly typed field is read losslessly or reset to its default, logged, and the file as it was (also before a migration) is kept as `.unreadable-<timestamp>` by copy, never by move, before the next save. A newer version or structural damage (bad JSON, a record without text, bad or duplicate ids) fails closed at startup. Its semantic index is an in-memory float32 numpy matrix, re-embedded from record text on every start and never written (FAISS was dropped: its libomp crashed beside torch's on macOS); `memory.index_file` is ignored.
  - `conversations.sqlite3`: the UI archive, built from bus events. It is a second history and can diverge from `chat_history.json`.
  - `tasks.sqlite3` (`app_core/persistence/tasks.py`): revision-checked, and shared with `Code/task_mcp_server.py`.
  - `tool_approvals.json` (`app_core/tools/approval.py`): rules belong to `(source, name)`, so a server's tool never inherits a built-in's rule. A file from before sources (`{name: bool}`) loads as legacy rules, which apply to Riko's tool of that name and, for a server's tool, only as 'ask first'; it is rewritten as version 2 on the next save. Unreadable or newer files fail closed (every call asks). Each save also writes a top-level `{name: bool}` mirror (ask first when any source asks first), which builds before sources read, so a downgrade fails closed.
  - The whiteboard, desktop, initiative and Discord JSON files, plus `wake_words/`.
- Also under the data root: `logs/debug.log` (rotating, secrets redacted), and emotion-probe datasets and weights under `models/` (`app_core/emotion/probe_storage.py`).

### Configuration and settings
- `load_config` (`app_core/configuration/config.py`) reads `$RIKO_CONFIG`, or `./character_config.yaml`, with PyYAML; a missing file silently yields defaults (provider `openai`). Relative paths resolve against the YAML's directory (`AppConfig.root`). Only `runtime`, `tools`, `memory` and `emotion` are typed dataclasses; other sections are read from `config.raw`. `RuntimeConfig` also declares the background budgets (`initiative_n_ctx`, `initiative_max_output_tokens`, `reflection_n_ctx`), which `load_config` fills from `initiative.*` and `memory.reflection_context_window_tokens`, the keys Settings edits them under.
- `character_config.yaml` is gitignored and no template is committed. `electron/main.cjs` also parses it at launch and aborts if it is missing.
- The Settings UI goes through `SettingsStore` (`app_core/configuration/settings_store.py`, module-level `LOCK`):
  - GET returns values, fields and a sha256 `revision`.
  - Validate writes a temporary `.settings-validation-*.yaml` beside the config and runs `load_config` on it.
  - PUT re-checks the revision (409 on conflict), keeps `character_config.yaml.previous`, and writes via mkstemp + fsync + `os.replace`. ruamel preserves comments and unknown keys.
- Only keys already in the YAML or defaulted in `SettingsStore._values` are editable, and each type is inferred from the current value. To add a setting:
  1. Give it a default in `_values`, plus entries in `ENUMS`, `RANGES`, `HELP` and `LABELS`.
  2. For it to apply without a restart, also update the restart flags in `field()`, `restart_required` in `save()`, and `save_settings` in `Code/desktop_server.py`.
- Applied live: `avatar.*`, `runtime.pause_background_on_live`, and `emotion.probe.interval_tokens` (if the probe was enabled at load). Everything else needs a Python restart. Electron reads `desktop.shortcuts`, `desktop.debug` and `presets.default.name` only at launch. `persistent_memories/initiative_settings.json` overrides the YAML `initiative` section.
- The backend's PyYAML parses YAML 1.1; ruamel and Electron's `yaml` parse 1.2. They disagree on `yes`/`no`/`on`/`off`.

### Electron ↔ backend contract
- `http://127.0.0.1:8765` is hard-coded in `electron/src/api.mjs`, `electron/main.cjs` and several components. CORS allows `null` (the packaged `file://` renderer) and the Vite origin.
- Every HTTP and WebSocket request needs `Authorization: Bearer <token>` and a loopback Host; WebSockets also need an app Origin (`LocalAPIGuard` in `app_core/desktop/api_guard.py`). The token and a separate confirmation key are fresh on every backend start, minted only after `run_server.py` has bound 127.0.0.1:8765 (before the model loads), and removed from the backend's environment so children never inherit them:
  - Packaged: Electron generates both and passes `RIKO_API_TOKEN`/`RIKO_CONFIRM_KEY` to the backend it spawns; nothing is written to disk. Main sends the token only after the backend prints `RIKO_BACKEND_LISTENING` on stdout (`watchListening` in `electron/release.cjs`), and stops when it exits.
  - Dev: the backend writes `persistent_memories/api_token` and `confirm_key` (mode 0600) beside the config; Electron main re-reads them when they change.
  - Electron main injects the header for every renderer request to `127.0.0.1:8765` (`injectApiToken` in `electron/main.cjs`), so renderer code never handles the token; main's own requests use `backendFetch`. The Discord worker gets `RIKO_API_TOKEN` from its launcher and exits when its stdin pipe closes, i.e. with that backend (`RIKO_EXIT_WITH_BACKEND`); started by hand, `client_token()` reads the file on every reconnect. Use `127.0.0.1`, not `localhost`, which may resolve to `::1`.
  - Tests use `client_for(backend)` in `tests/test_desktop_api.py`. API docs are served only with `RIKO_DEV=1`.
- Security-sensitive changes (`security_sensitive()` in `Code/desktop_server.py`: anything that loads code, models or libraries, starts programs, widens file access or sends data elsewhere, judged by key name, by every leaf of a section saved at once, and by values that are URLs or absolute paths; turning tool approval off; Discord access) return 428 with a single-use `confirm` challenge. `request()` in `electron/src/api.mjs` asks Electron main (`confirm-security-change`), which shows a native dialog and signs the challenge with the confirmation key, which never goes over the wire. A new setting that can do any of those things must be covered by `security_sensitive()`.
- `/ws/events` (`app_core/events/stream.py`) sends `state.snapshot`, then `resource.snapshot`, then every bus event. A client with 100 queued events is closed with code 1013.
- All windows share one socket (`electron/src/event_connection.mjs`, 1 s reconnect). Subscribe via `connectEvents`, `useRuntime` or `useResource`, and never poll: `electron/src/subscription_guard.test.mjs` forbids `setInterval`.
- Every `DesktopState` change republishes a full `state.snapshot`. Panels read `resource.<topic>` events from `ResourceEvents` (`app_core/events/resources.py`); a new topic needs an `observe()` mapping and a `resource_getters()` entry.
- `POST /api/chat` returns only after the full reply; deltas arrive over the socket. Renderer acknowledgements are authoritative (`/api/surfaces/result`, `/api/avatar/animation/result`).

### Discord
`Code/discord_bot.py` is a separate process and only a backend client; it loads no model. A failed Discord send or edit costs only that chunk (`StreamReply` retries it on the next flush with the same per-chunk nonce, so Discord never posts it twice; `finish()` is idempotent), and the turn queue survives transport errors and is restarted by a done-callback if it ever dies. It holds one WebSocket at `/ws/discord/client?instance=<uuid>`, which carries only the events `bot.py` handles (`client_event_filter` in `app_core/integrations/discord/api.py`: its own turns' deltas, reasoning and approval requests, approvals, Discord and whiteboard resources, initiative messages), and calls `/api/discord/*` (`app_core/integrations/discord/api.py`). Start it with `POST /api/discord/start` or the tray menu, or by hand once the backend runs. Credentials go in a local `.env` (template: `.env.discord.example`).

### Dev vs packaged
- **Dev:** the repo root is both the cwd and the data root.
- **Packaged, first launch:** Electron shows `#/setup`, which writes `<data>/character_config.yaml` (never overwriting) and `data-location.json` in Electron's userData (`electron/release.cjs`).
- **Packaged, later launches:**
  - Electron spawns `backend/riko-backend` with `RIKO_MANAGED=1`, `RIKO_DATA_DIR`, `RIKO_CONFIG` and `RIKO_BUNDLE_ROOT`.
  - Hugging Face and torch caches go under `<data>/models`.
  - A `shutdown` line or EOF on stdin stops the backend (it dumps stacks and exits itself after 14 s); Electron sends SIGTERM after 15 s and SIGKILL 3 s later. On macOS the backend's PATH gets the Homebrew prefixes so MCP servers and ffmpeg resolve (`finderPath`).
  - `runtime.native_library: bundled:<cuda|vulkan>` resolves to `$RIKO_BUNDLE_ROOT/native/<backend>/`.

## Conventions and gotchas
- Whole-file JSON writes go through `persistence/atomic.py` `atomic_write`: a unique temp file beside the target, fsync (`F_FULLFSYNC` on macOS), `os.replace` retried briefly on `PermissionError` (Windows sharing violations from antivirus or indexers), then a best-effort directory fsync; new files are 0600, and temporaries older than 10 minutes (left by a killed process) are swept. Backups (`*.unreadable-*`) and temporaries under `persistent_memories/` are gitignored. The settings YAML, the API secrets and the whiteboard keep their own writes. Stores fail closed rather than resetting user data: keep an unreadable file with `persistence/preserve.py` (`<name>.unreadable-<timestamp>`), or refuse to save over it.
- Optimistic concurrency uses revisions throughout: the settings `revision`, task `expected_revision` (`TaskConflict` → 409), the Discord access revision, memory-record revisions, and whiteboard `board_revision`.
- File paths supplied by the renderer or the model must go through `resolve_media` (`app_core/desktop/media.py`: approved roots plus an extension allowlist).
- Heavy dependencies (torch, faster_whisper, sounddevice, silero_vad, sentence_transformers, openai, huggingface_hub) are imported lazily, and tests swap them through `sys.modules`. Services accept `start=False` / `start_worker=False`. Tests must close services and unsubscribe from the global `event_bus` in `finally`.
- The `app_core/` root may contain only `__init__.py` and `factory.py`, and every relative import must resolve (`tests/test_app_core_structure.py`). `app_core/__init__.py` is a lazy facade (PEP 562): its public names load on first use, so a leaf import (a store, the tool worker, `task_mcp_server.py`) loads only what it uses. Inside app_core, import from the defining module, never the facade, `factory.py` or an entry point.
- `app_core/kernel/` holds the leaf utilities every package uses (messages, streaming, output_filter, cancellation, workers, lifecycle, metrics, torch_device, background_budget) and imports nothing else from app_core. The old paths (`conversation/messages.py`, `runtime/workers.py`, ...) are re-export shims for one release, listed in `SHIMS` in `tests/test_app_core_structure.py`. `tests/test_package_boundaries.py` pins every cross-package import, module-level or inside a function, in `EDGES` and forbids cycles: a new edge fails until it is added there, and a vanished one until it is removed.
- Tools (`app_core/tools/`) share one `Tool` shape (`tool.py`: name, description, input_schema, `choices(arguments)`, `prepare`, `execute`, plus `isolated`, `read_only`, `owner` and `source`) and all enter through `ToolRegistry.register(tool, *, source, replace=False)`: `register_local` adapts built-in and desktop tool objects, `register_mcp` an MCP client's tools, and SessionManager registers its own tools the same way. `source` is `RIKO` for Riko's own tools, whose names must match `^[a-zA-Z0-9_-]{1,64}$` and never clash (a clash raises), or `mcp:<server>` for an `mcp.json` server, whose tool runs as `<server>__<name>` (warning logged) when its name is invalid or taken, even by one of Riko's tools registered later, and is left out when that fails too. Built-ins run in an isolated subprocess because `BaseTool.ISOLATED` says so (`isolation.py`), not because of their module path; desktop tools run in-process and their `execute` signature is their schema. Tool-specific input rules stay in the tool (`choices(arguments)` leaves out what a call need not choose). The initiative check offers exactly the `read_only` tools; only Riko's own can be (TaskMCP's `readOnlyHint` marks `task_list` and `task_get`), never a server's. `registry.py` is policy only: schemas are `schema.py`, the stdio and HTTP transports `mcp/`, and the old names stay importable from `registry.py` for one release. `ToolRegistry.execute` waits in slices so Stop ends a call at once: it kills that call's worker, or sends a stdio MCP server `notifications/cancelled`, and returns an error result. `mcp.json` (copied from `mcp.json.example`) loads only if `tools.mcp_config` points at it. `ToolRegistry` reports tool activity and MCP load failures to the observer it is given (`activity=`; the factory passes `DesktopState`), never the desktop singleton, and desktop tools act through the `DesktopServices` it is given (`desktop=`: media resolver, effect library, gestures, walking).
- Electron:
  - Pure logic lives in `.mjs`/`.cjs` files, each with a sibling `*.test.mjs`.
  - Several tests regex-match the source text of `electron/main.cjs`, the CSS and some components, so refactors must update those tests too.
  - `electron/vite.config.mjs` passes `react` without calling it, so JSX uses the classic transform and every `.jsx` must `import React`.
- Style: the Python and JS are dense, often with several statements per line; match the surrounding code.
- The README links to `docs/*.md`, but `/docs` is gitignored and absent.
- `tools/migrate_legacy_memories.py` and `tools/migrate_legacy_chat_history.py` only dry-run unless given `--write`; run them with the app stopped.

## Platform status

Releases ship CUDA and Vulkan bundles for Windows and Linux x64 and a Metal bundle in an arm64 macOS DMG (macOS 14+, ad-hoc signed unless the MAC_* signing/notarization secrets exist); nothing builds, packages, detects or tests ROCm/HIP yet (one manifest entry plus a build container). The Python inference layer is backend-agnostic: the backend is whatever llama.cpp build `runtime.native_library` loads, or whatever llama-server `runtime.provider: llama_server` talks to (any backend, without the emotion probe; checked against stock llama-server b11408 on Apple Silicon). The patched bridge, including the emotion probe, has been built and run on Apple Silicon Metal at the current pin.

Backend and device assumptions live here:
- **Native build and packaging:**
  - `electron/native_backends.json` is the one manifest of backends (cuda, vulkan, metal), the platforms that ship each, per-OS library names (`riko-native.dll`, `libriko-native.so`, `libriko-native.dylib`), shared-library patterns, rpaths (`$ORIGIN`, `@loader_path`) and CMake switches. `app_core/configuration/native_backends.py`, `electron/native_backends.cjs`, `config.py` (`bundled:<backend>`), `release.cjs` (hardware detection runs only the current OS's detect commands: none on macOS) and `first_setup.jsx` read it; naming is tested with explicit per-platform tables on every host.
  - `tools/release/build.py` builds the manifest's backends for the host OS, keeps versioned library symlinks, renders the macOS icon from `assets/logo.svg`, puts `Code/` on PyInstaller's path (without it `--collect-submodules process` silently froze none of Riko's dynamically imported modules) and repeats `--release-check` inside the packaged app (`--check-app`).
  - `.github/workflows/release.yml`: windows-2022 and ubuntu-22.04 (CUDA 12.4.1, Vulkan) and macos-15 (Metal DMG).
  - `electron/electron-builder.yml`: NSIS, AppImage, deb and a hardened-runtime mac dmg with `electron/build/entitlements.mac.plist` (allow-jit, audio-input, disable-library-validation, each needed by V8, the microphone or torch) and the `electron/build/mac_sign.cjs` signing hook. Packaged macOS asks for microphone access before starting the backend.
- **Library loading:** `os.add_dll_directory` is called only on Windows (`app_core/inference/llama_native.py`, `Code/run_server.py`).
- **NVIDIA-only telemetry:** `app_core/resources/gpu_memory.py` (nvidia-smi, DXGI vendor `0x10de`, PowerShell counters) and the CUDA rows in `app_core/resources/vram_estimate.py`.
- **ASR:** every faster-whisper model is built by `app_core/audio/asr.py:create_whisper`, and the session keeps one (`AsrService`). Defaults are `auto`/`default`, resolved from what CTranslate2 reports (CPU int8 on macOS, which has no CTranslate2 GPU backend); an unsupported configured pair falls back once with a warning, and Settings refuses one when it is edited. GPU ASR on Metal or ROCm needs a different engine (whisper.cpp, mlx-whisper, or a HIP-built CTranslate2).
- **Torch devices:** `app_core/kernel/torch_device.py` accepts `auto`/`cpu`/`cuda[:n]`/`mps` (ROCm torch reports `cuda`). Julia maps `mps` to CPU until upstream moves inputs for MPS, retries a failed GPU load on CPU, and restores torch's thread count after loading. `memory.device` covers the memory classifier and embedder; the settings `ENUMS` and `tests/test_llama_native.py` pin the lists.
- **Windows-only behaviour:** `WindowsActivity` in `app_core/runtime/initiative.py`, the Win32 pointer hooks in `electron/main.cjs`, and the acrylic material in `electron/window_material.cjs`.
